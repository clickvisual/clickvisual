# 设计：ClickVisual v2 独立前端壳层

## 范围

本设计定义 ClickVisual v2 的首期落地边界：

- 独立新前端应用
- `v1` 与 `v2` 共存，并支持随时切换
- 五模块完整可运行壳子
- `v2` 专用接口/聚合接口
- 平台共享层 + 垂直业务域组织方式
- AI 动作的结构化入口与降级策略
- 五个模块统一视觉重做，并以 `v2/stitch/` 设计稿作为视觉真源

## 视觉重做策略

### 视觉真源

本轮视觉改造以以下资产为唯一参考：

- `v2/stitch/chronos_amber/DESIGN.md`
- `v2/stitch/dashboard_overview_with_ai_suggestions/code.html`
- `v2/stitch/base_query_interface_aliyun_sls_style/code.html`
- `v2/stitch/scheduled_reports_dingtalk_push/code.html`
- `v2/stitch/alerting_system_dingtalk_notification/code.html`
- `v2/stitch/configuration_center_ai_dingtalk_config/code.html`

实现时不以当前 `ui-v2` 朴素壳层为视觉基线，而是以设计稿为主、现有可运行行为为辅进行重建。

### 统一视觉底座

五个模块必须共享同一套视觉基础，而不是分别堆页面：

- 统一字体策略：标题与关键数字使用 `Space Grotesk`，正文与表单使用 `Inter`
- 统一色板与层次：采用 `surface / surface-container-* / primary / tertiary` 体系
- 统一布局语言：玻璃侧边栏、固定顶栏、非对称主内容区
- 统一“无边框”规则：用背景层级和表面抬升替代常规 `1px border`
- 统一主按钮语言：橘色渐变 CTA
- 统一信息容器：优先通过区块、分栏和 tonal layer 组织内容

### 模块重做映射

五个模块的页面形态按如下映射重做：

- `overview`
  - 参考 `dashboard_overview_with_ai_suggestions`
  - 必须包含 KPI、趋势、热点、AI 建议、最近事件区
- `query`
  - 参考 `base_query_interface_aliyun_sls_style`
  - 必须包含顶部筛选、查询编辑区、结果区、右侧辅助区
- `report`
  - 参考 `scheduled_reports_dingtalk_push`
  - 在保留现有调度/预览/推送闭环的前提下重做视觉与布局
- `alert`
  - 参考 `alerting_system_dingtalk_notification`
  - 必须包含规则列表、状态概览、事件/通知入口区
- `settings`
  - 参考 `configuration_center_ai_dingtalk_config`
  - 必须包含配置分区、连接态与 AI / DingTalk 子区域

### 实施约束

- 共享框架先行，五个模块随后统一替换
- 不允许先做一个模块的高保真、其它模块仍保持当前粗糙壳层太久
- 已具备真实功能的 `report` 行为链路必须保留
- 允许其余模块先使用稳定 mock/fixture，但页面信息架构和视觉需直接对齐设计稿
- 任何新增共享组件都应服务多个模块，避免为单页设计稿临时堆一次性组件

## 架构设计

### 整体形态

`v2` 采用双层结构：

- 前端层：独立新前端应用，负责设计系统、应用壳层、统一筛选语义、AI 动作入口和五个业务域页面
- 后端层：新增 `v2` 页面契约层，对外提供总览、查询、报表、告警、配置中心和 AI 动作所需的聚合接口；内部调用现有或新增的查询、告警、报表、通知、AI 能力

在系统层面，`v1` 与 `v2` 采用双前端并存模式：

- `v1` 继续保留现有入口与现有页面契约
- `v2` 使用独立路由前缀与独立页面契约
- 用户可以从统一入口显式切换版本，并在需要时回退到 `v1`
- 默认进入哪个版本可以由用户偏好、灰度开关或平台配置决定

### 平台共享层

平台共享层负责：

- 应用壳层与导航
- 版本切换入口与版本偏好记忆
- 鉴权与租户/项目上下文
- 全局时间范围与服务筛选
- 面包屑与通知中心
- 统一设计系统与基础组件
- 通用查询参数模型
- AI 快捷动作框架

### 垂直业务域

五个业务域分别负责：

- `overview`
  - KPI、趋势图、热点分布、AI 建议、最近告警、最近报表
- `query`
  - DSL/SQL 输入、查询执行、原始日志、聚合统计、Trace、JSON 视图、保存查询、图表生成
- `report`
  - 报表列表、报表编辑、调度配置、预览、钉钉投递对象
- `alert`
  - 告警规则、规则编辑、试跑、事件列表、恢复确认、钉钉通知
- `settings`
  - ClickHouse 数据源、Schema 映射、钉钉配置、AI 配置

## 数据流与契约

### 前端状态模型

前端只维护两类状态：

- 页面态：当前 tab、当前筛选条件、选中记录、展开状态、分页状态、图表配置等
- 用户意图态：当前 query、当前规则草稿、当前报表草稿、当前保存动作、当前 AI action 请求等

前端不直接承载 ClickHouse 底层实现细节，不直接拼接多个旧接口数据结构来合成页面。

### 契约优先的 API 形态

`v2` 接口按页面能力组织：

- `/v2/overview/*`
  - KPI、趋势、热点、最近告警、最近报表、AI 总结
- `/v2/query/*`
  - 查询执行、字段提示、语法建议、保存查询、图表生成
- `/v2/reports/*`
  - 报表 CRUD、模板、预览、调度、投递对象
- `/v2/alerts/*`
  - 规则 CRUD、规则试跑、事件列表、恢复确认
- `/v2/settings/*`
  - 数据源、Schema、钉钉、AI 配置
- `/v2/ai/actions/*`
  - 优化 SQL、生成告警、生成报表、总结异常等结构化 AI 动作

### AI 动作模型

AI 能力绑定在明确业务上下文中：

- 输入固定为当前页面上下文、筛选条件、样本数据和用户触发动作
- 输出固定为结构化建议与可一键应用结果
- 所有 AI 动作都应支持失败提示、禁用状态和审计追踪

## 前端应用结构

建议新前端应用独立目录为 `ui-v2/`。

### 目录模型

- `app/`
  - 应用入口、路由、layout、providers 配置
- `shared/`
  - 设计系统基础组件、通用 hooks、图表容器、通用筛选器、时间范围模型、表格工具
- `entities/`
  - 跨模块核心模型，例如 `timeRange`、`serviceScope`、`savedQuery`、`alertRule`、`reportTemplate`、`aiAction`
- `domains/overview`
- `domains/query`
- `domains/report`
- `domains/alert`
- `domains/settings`

### 路由模型

首期即采用最终路由形态：

- `/overview`
- `/query`
- `/dashboards`
- `/reports`
- `/alerts/rules`
- `/alerts/events`
- `/ai`
- `/settings/datasource`
- `/settings/schema`
- `/settings/dingtalk`
- `/settings/ai`

同时保留 `v1` 的既有路由入口。路由约束如下：

- `v1` 继续使用现有路由，例如 `/query`、`/configure`、`/alarm/*`
- `v2` 使用独立前缀或独立挂载空间，避免与 `v1` 冲突
- 系统提供显式“切换到 v2 / 返回 v1”入口
- 切换动作不应破坏当前登录态与租户上下文

### 组件归属

设计系统只承载纯视觉和交互原子，例如：

- 按钮
- 卡片
- 徽标
- 查询编辑器外壳
- 图表容器
- 表格外壳
- AI 建议卡片
- 空态、错误态、加载态

以下组件保留在业务域内，不进入 `shared/`：

- 告警规则编辑器
- 报表调度编辑器
- 配置中心连接测试面板
- 查询页结果标签页容器

## 可运行壳子标准

### 必备行为

每个模块必须具备：

- 可进入的正式页面路由
- 至少一条真实可操作的主流程
- `loading / empty / error` 三类数据态
- 提交中、成功、失败和可恢复提示
- 最小筛选与分页或分段加载能力
- 表单草稿态、校验态与保存回显

版本共存还必须具备：

- 用户可以从 `v1` 进入 `v2`
- 用户可以从 `v2` 返回 `v1`
- 版本切换入口对用户可见且语义明确
- 版本切换失败时有明确提示，不允许静默跳回或白屏
- 视觉层必须具备与设计稿一致的主框架、页面层次和关键区域结构，不允许只保留标题加说明文案

### 降级策略

前端支持 mock-first，但必须 contract-stable：

- 若真实接口未完成，可临时使用 mock 或静态 fixture
- mock 数据结构必须遵守最终 `v2` 接口契约
- 切换真实接口时，不允许重写页面状态模型

AI 相关能力必须可降级：

- AI 服务不可用时，基础查询、规则编辑、报表配置仍能完成
- AI 动作在不可用时应明确禁用或报错，不允许静默失效

### 验收分层

1. 结构验收
   - 独立新前端应用存在
   - `v1` 与 `v2` 入口同时存在
   - 完整路由存在
   - 统一壳层与五模块页面可访问
   - 五模块页面都已接入统一视觉底座
2. 交互验收
   - 可从 `v1` 切换到 `v2`
   - 可从 `v2` 返回 `v1`
   - 总览可加载聚合数据
   - 查询可执行一次 DSL/SQL
   - 报表可新建并预览
   - 告警规则可新建并试跑
   - 配置中心可保存至少一类配置
3. 契约验收
   - 新前端页面只依赖 `v2` 契约层
   - 不直接复用旧 `ui/` 页面代码
   - 不直接耦合零散旧接口
4. 视觉验收
   - 共享侧边栏、顶栏、表面层级与主按钮风格统一
   - `overview / query / report / alert / settings` 五页与 `v2/stitch/` 信息架构一致
   - 页面首屏不再呈现工程占位态或默认后台卡片风

## 后端边界

`v2` 页面契约层可以实现为 API/BFF，对前端暴露稳定页面模型；其下逐步复用或替换现有能力。

版本共存期间的后端约束如下：

- `v1` 继续使用现有页面接口
- `v2` 使用新的 `/v2/*` 页面契约
- 两个版本可以共享底层领域服务，但不共享页面契约层
- 灰度放量与默认版本策略应在入口层或配置层控制，而不是混入页面实现逻辑

推荐的后端能力边界：

- 查询能力：DSL/SQL 执行、字段提示、聚合结果、Trace 聚合
- 总览能力：KPI、趋势、热点和最近事件聚合
- 告警能力：规则持久化、试跑、事件生成、恢复逻辑
- 报表能力：模板、调度、预览和输出
- 通知能力：钉钉 webhook、签名、重试、幂等
- AI 能力：总结、建议、规则生成、查询优化

## 任务映射原则

后续实现任务必须从当前 change 的 `tasks.md` 分派，不允许在 planning files 中维护一套竞争性主任务列表。

规划文件仅用于：

- 当前 owner
- 最新发现
- 阻塞原因
- 恢复锚点
- 执行日志
