# ClickVisual v2 Design Spec

## Background

ClickVisual 现有正式前端位于 `ui/`，技术栈为 Umi 4 + Ant Design Pro + React 18。仓库内新增的 `v2/` 目录目前包含一套静态页面原型与设计语言，覆盖以下五个业务模块：

1. 大盘总览（含 AI 建议）
2. 基础查询功能
3. 定时报表（钉钉推送）
4. 告警系统（钉钉推送）
5. 配置中心（AI 配置 + 钉钉通知配置）

本次 v2 目标不是继续在旧前端内渐进演进，而是在仓库内建设一个独立新前端应用，承接新的橘色浅色主题、交互结构和 AI 入口。同时，允许在规格中同步定义一批 `v2` 专用接口/聚合接口，避免新页面被旧接口和旧页面模型绑定。

首期范围不是局部 MVP，而是五个模块都先具备“可运行壳子”。

## Goals

- 在仓库中建立独立的新前端应用，作为 ClickVisual v2 的正式承载体。
- 将五个核心模块统一到一套新的信息架构、设计系统和平台壳层中。
- 定义面向页面能力的 `v2` 接口契约，而不是复用零散旧接口拼装页面。
- 让每个模块在首期都具备最小可操作主流程，满足“可运行壳子”标准。
- 为后续实现计划提供清晰的模块边界、任务依赖和验收标准。

## Non-Goals

- 本规格不要求本轮直接实现全部后端深层业务逻辑。
- 本规格不要求替换现有 `ui/` 主应用。
- 本规格不要求首期完成所有 AI 能力的真实算法效果，只要求保留结构化入口和可降级路径。
- 本规格不要求首期解决所有 ClickHouse 查询优化与性能问题。

## Chosen Approach

采用“方案 A”：独立新前端应用 + `v2` 专用聚合接口 + 五个业务模块按垂直域组织。

该方案的核心理由：

- 用户已明确要求独立新前端应用，不受当前 `ui/` 老栈约束。
- 用户已明确要求五模块首期同时形成可运行壳子，不适合先做旧接口适配层再二次重构。
- 用户已允许同步定义 `v2` 专用接口，适合直接围绕新页面能力建立契约。

## System Architecture

### Overall shape

`v2` 采用双层结构：

- 前端层：独立新前端应用，负责设计系统、应用壳层、统一筛选语义、AI 动作入口和五个业务域页面。
- 后端层：新增 `v2` 页面契约层，对外提供总览、查询、报表、告警、配置中心和 AI 动作所需的聚合接口；内部再调用现有或新增的查询、告警、报表、通知、AI 等服务能力。

### Shared platform layer

平台共享层负责：

- 应用壳层与导航
- 鉴权与租户/项目上下文
- 全局时间范围与服务筛选
- 面包屑与通知中心
- 统一设计系统与基础组件
- 通用查询参数模型
- AI 快捷动作框架

### Vertical domains

五个业务域分别负责：

- `overview`
  - KPI、趋势图、热点分布、AI 建议、最近告警、最近报表
- `query`
  - DSL/SQL 输入、查询执行、原始日志、聚合统计、Trace、JSON 视图、保存查询、图表生成
- `report`
  - 报表列表、报表编辑、调度配置、预览、钉钉投递对象
- `alert`
  - 告警规则、规则编辑、试跑、事件列表、恢复确认、钉钉通知
- `settings`
  - ClickHouse 数据源、Schema 映射、钉钉配置、AI 配置

平台层与业务域的原则是：共享壳层与共享能力，但每个业务域独立维护自己的页面容器、模块状态、接口适配和局部组件。

## Data Flow And API Contract

### Frontend state model

前端只维护两类状态：

- 页面态：当前 tab、当前筛选条件、选中记录、展开状态、分页状态、图表配置等
- 用户意图态：当前 query、当前规则草稿、当前报表草稿、当前保存动作、当前 AI action 请求等

前端不直接承载 ClickHouse 底层实现细节，不直接拼接多个旧接口数据结构来合成页面。

### Contract-first API shape

`v2` 接口按页面能力组织，而不是按底层表或历史模块组织。最少应包含以下接口分组：

- `/v2/overview/*`
  - KPI、趋势、热点、最近告警、最近报表、AI 总结
- `/v2/query/*`
  - 查询执行、字段提示、语法建议、保存查询、图表生成
- `/v2/reports/*`
  - 报表 CRUD、模板、预览、调度、投递对象
- `/v2/alerts/*`
  - 规则 CRUD、规则试跑、事件列表、恢复确认
- `/v2/settings/*`
  - 数据源、Schema、钉钉、AI 配置
- `/v2/ai/actions/*`
  - 优化 SQL、生成告警、生成报表、总结异常等结构化 AI 动作

### AI action model

AI 能力不以自由聊天的方式嵌入，而是绑定在明确业务上下文中：

- 输入固定为当前页面上下文、筛选条件、样本数据和用户触发动作
- 输出固定为结构化建议与可一键应用结果
- 所有 AI 动作都应支持失败提示、禁用状态和审计追踪

这保证 AI 功能在首期即可接入页面主流程，同时在服务不可用时仍能安全降级。

## Frontend Application Structure

建议新前端应用独立目录为 `ui-v2/`。

### Directory model

- `app/`
  - 应用入口、路由、layout、providers
- `shared/`
  - 设计系统基础组件、通用 hooks、图表容器、通用筛选器、时间范围模型、表格工具
- `entities/`
  - 跨模块核心模型，例如 `timeRange`、`serviceScope`、`savedQuery`、`alertRule`、`reportTemplate`、`aiAction`
- `domains/overview`
- `domains/query`
- `domains/report`
- `domains/alert`
- `domains/settings`

### Routing model

首期即采用最终路由形态，而不是临时测试路由：

- `/overview`
- `/query`
- `/dashboards`
- `/reports`
- `/alerts/rules`
- `/alerts/events`
- `/ai`
- `/settings/datasource`
- `/settings/schema`
- `/settings/dingtalk`
- `/settings/ai`

即便个别页面首期只达到壳子级别，也维持稳定路由形态，避免后续重新调整导航、权限、分享链接和钉钉消息跳转目标。

### Component ownership

设计系统只承载纯视觉和交互原子，例如：

- Button
- Card
- Badge
- Query Editor Shell
- Chart Container
- Table Shell
- AI Suggestion Card
- Empty/Error/Loading State

以下组件必须保留在业务域内，不进入 `shared/`：

- 告警规则编辑器
- 报表调度编辑器
- 配置中心连接测试面板
- 查询页结果 tabs 容器

## Runtime Shell Standard

“完整五模块可运行壳子”的定义如下。

### Required user-visible behavior

每个模块必须具备：

- 可进入的正式页面路由
- 至少一条真实可操作的主流程
- `loading / empty / error` 三类数据态
- 提交中、成功、失败和可恢复提示
- 最小筛选与分页或分段加载能力
- 表单草稿态、校验态与保存回显

### Degrade strategy

前端支持 mock-first，但必须 contract-stable：

- 若真实接口未完成，可临时使用 mock 或静态 fixture
- mock 数据结构必须遵守最终 `v2` 接口契约
- 后续切换真实接口时，不允许重写页面状态模型

AI 相关能力必须可降级：

- AI 服务不可用时，基础查询、规则编辑、报表配置仍能完成
- AI 动作在不可用时应明确禁用或报错，不允许静默失效

### Acceptance layers

首期验收分三层：

1. 结构验收
   - 独立新前端应用存在
   - 完整路由存在
   - 统一壳层与五模块页面可访问
2. 交互验收
   - 总览可加载聚合数据
   - 查询可执行一次 DSL/SQL
   - 报表可新建并预览
   - 告警规则可新建并试跑
   - 配置中心可保存至少一类配置
3. 契约验收
   - 新前端页面只依赖 `v2` 契约层
   - 不直接复用旧 `ui/` 页面代码
   - 不直接耦合零散旧接口

## Backend Boundary

`v2` 页面契约层可以实现为 API/BFF，对前端暴露稳定页面模型；其下可以逐步复用或替换现有能力。

推荐的后端能力边界如下：

- 查询能力：负责 DSL/SQL 执行、字段提示、聚合结果、Trace 聚合
- 总览能力：负责 KPI、趋势、热点和最近事件的聚合组装
- 告警能力：负责规则持久化、试跑、事件生成、恢复逻辑
- 报表能力：负责模板、调度、预览和输出
- 通知能力：负责钉钉 webhook、签名、重试、幂等
- AI 能力：负责总结、建议、规则生成、查询优化

这意味着前端面对的是稳定页面契约，而不是底层服务拓扑。

## Risks And Tradeoffs

- 新前端与旧前端并存，会带来一段时期的双应用维护成本。
- `v2` 聚合接口首期定义不清，会导致前端页面模型后续返工。
- 五模块同时进入首期范围，要求必须严格控制“可运行壳子”的边界，避免在首轮就追求全部深度能力。
- AI 功能如果不做结构化约束，后续会拖累页面稳定性和可测试性。

## Initial Task Decomposition

建议在后续实现计划中按以下顺序拆分任务：

1. 建立 `ui-v2/` 应用壳层、路由、基础工程配置与设计系统基础令牌
2. 建立平台共享层：全局 layout、导航、筛选器、时间范围、通知与页面骨架
3. 定义 `v2` 接口契约与 mock 数据模型，覆盖五个模块主流程
4. 落地 `overview` 与 `query` 模块页面壳子及接口接入
5. 落地 `report` 与 `alert` 模块页面壳子及接口接入
6. 落地 `settings` 模块页面壳子及接口接入
7. 补齐 AI action 入口、统一错误处理、降级逻辑与状态反馈
8. 完成联调、验证与首期验收

## Open Decisions Resolved

- `v2` 使用独立新前端应用，不在现有 `ui/` 内渐进改造
- 首期范围为五个模块全部形成可运行壳子
- 允许在规格中同步定义 `v2` 专用接口/聚合接口
- 采用平台共享层 + 五个垂直业务域的组织方式
- AI 能力采用结构化 action 入口，而非自由聊天入口
