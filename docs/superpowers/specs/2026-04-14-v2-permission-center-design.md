# v2 权限中心设计

## 背景

当前 v1 已具备完整的权限管理能力，分散在以下入口：

- `/sys/pms` 负责角色管理与 root 授权
- `/sys/instances` 负责实例配置与实例下角色授权
- 用户管理负责用户创建、编辑、删除与重置密码

当前 v2 仅实现了配置中心中的数据源与通知管理，尚未提供权限管理主流程。与此同时，后端已经存在部分可复用能力：

- `api/v2/base/users` 已提供用户管理接口
- `api/v1/pms/*` 仍承载角色、root、实例角色授权等权限能力
- v2 业务接口已经广泛依赖现有 `pmsplugin` 和权限检查逻辑

本次目标不是把 v1 页面逐页搬运到 v2，而是在保持现有权限模型基本不变的前提下，设计更合理的 v2 权限配置流程，并完成首期实施。

## 目标

- 在 v2 中实现完整的权限管理能力，覆盖：
  - 角色管理
  - 实例与角色绑定
  - 用户与角色绑定
  - 用户管理
  - root 用户授权
- 优化 v1 分散式配置流程，减少跨页面跳转
- 尽量复用现有权限模型、权限校验和存量接口，降低迁移风险
- 为后续全面切换到 v2 留出兼容空间

## 非目标

- 本次不重写底层权限模型
- 本次不变更已有权限校验语义，如 `root`、默认角色、自定义角色、实例级授权关系
- 本次不强制将所有 `api/v1/pms/*` 立即迁移为全新服务实现，但可按需提供 v2 聚合接口

## 现状问题

### v1 流程问题

v1 的权限配置流程以资源和功能页面为中心，存在以下问题：

- 用户管理、角色管理、实例授权入口彼此割裂
- 想回答“某个用户现在拥有哪些权限”时，需要在多个页面之间切换
- root 授权混在权限体系中，但风险等级远高于普通角色授权
- 对普通管理员来说，最常见的任务是“给某人开通某个实例权限”，而不是“在某个实例页面里逐层配置角色”

### v2 现状问题

- v2 路由中只有 `settings/datasource`
- 没有权限中心信息架构
- 没有角色、授权、root 管理的统一入口
- 用户管理虽然已有接口，但没有 v2 页面承载

## 设计原则

- 用户主线优先：默认围绕“用户当前拥有哪些权限”组织交互
- 角色模板次之：角色是模板定义，不应成为最高频入口
- 资源授权可追溯：仍然要保留实例视角，便于排查谁能访问某个实例
- root 隔离：root 授权必须单独分区，强化风险提醒和确认
- 兼容优先：首期复用现有权限模型与主要接口，优先完成可用迁移

## 方案对比

### 方案 A：v1 兼容搬运

把 v1 的角色管理、实例授权、用户管理、root 授权分别搬到 v2。

优点：

- 风险最低
- 后端改动最少
- 迁移速度快

缺点：

- 延续 v1 的割裂流程
- 用户主线不明显
- 长期仍需重构

### 方案 B：用户主线型权限中心

在 v2 中建立统一“权限中心”，按以下分区组织：

- 用户与授权
- 角色模板
- 资源范围
- Root 管理

优点：

- 最符合日常运维和授权动作
- 能显著减少跨页面跳转
- 兼容现有权限模型，改造成本可控

缺点：

- 需要新增聚合视图与更复杂交互
- 需要在前端做一定的数据整合

### 方案 C：向导式授权

通过 wizard 完成“选用户 -> 选角色 -> 选实例 -> 确认”。

优点：

- 首次开通顺手

缺点：

- 修改存量授权效率低
- 批量管理和排查不方便

### 结论

采用方案 B，即“用户主线型权限中心”。

## v2 信息架构

建议在 v2 中新增 `权限中心` 一级导航，包含以下子页面：

### 1. 用户与授权

定位：最高频入口。

能力：

- 用户列表、搜索、分页
- 创建用户
- 编辑用户信息
- 重置密码
- 删除用户
- 查看某个用户当前拥有的角色授权
- 给用户新增授权
- 调整或删除用户已有授权

页面结构：

- 左侧或上方为用户列表
- 主区域展示选中用户详情
- 权限详情区展示：
  - 普通权限
  - 按实例分组的角色
  - 每个角色下的 domain / scope

核心操作流：

1. 找到用户
2. 查看当前授权
3. 点击“新增授权”
4. 选择实例
5. 选择角色
6. 配置 domain 范围
7. 保存

### 2. 角色模板

定位：角色定义维护区。

能力：

- 查看角色列表
- 查看角色详情
- 创建角色
- 编辑角色
- 删除角色
- 区分默认角色与自定义角色
- 展示角色的：
  - 所属资源
  - sub-resources
  - acts

说明：

- 默认角色仅 root 可管理
- 自定义角色按资源归属校验权限

### 3. 资源范围

定位：实例视角的审计与排查入口。

能力：

- 查看实例列表
- 查看实例下所有角色授权关系
- 看到每个角色下有哪些用户、作用域是什么
- 从资源视角发起授权调整

说明：

- 这是保留 v1 资源视角的必要入口
- 但不作为默认主入口

### 4. Root 管理

定位：高风险能力单独隔离。

能力：

- 查看当前 root 用户列表
- 搜索并授予 root
- 撤销 root
- 展示高风险提醒
- 二次确认

说明：

- Root 管理页面在视觉上单独标识
- 与普通角色授权严格区分

## 推荐配置流程

### 普通授权流程

1. 进入“用户与授权”
2. 搜索或创建用户
3. 打开用户详情
4. 在“权限授权”区直接选择：
   - 实例
   - 角色
   - domain 范围
5. 保存并即时反馈结果

### 角色维护流程

1. 进入“角色模板”
2. 查看已有默认角色与自定义角色
3. 如需新增权限能力，先创建或编辑角色模板
4. 再回到“用户与授权”分配给用户

### Root 授权流程

1. 进入“Root 管理”
2. 明确风险提示
3. 搜索用户并授权或撤销
4. 二次确认

### 资源排查流程

1. 进入“资源范围”
2. 选择实例
3. 查看当前实例的角色与用户绑定关系
4. 如需调整，可直接修改或跳转回用户主线

## 后端能力评估

### 已存在且可复用

- 用户管理：
  - `GET /api/v2/base/users`
  - `POST /api/v2/base/users`
  - `PATCH /api/v2/base/users/:id`
  - `PATCH /api/v2/base/users/:id/password-reset`
  - `DELETE /api/v2/base/users/:id`
- 权限角色：
  - `GET /api/v1/pms/role`
  - `POST /api/v1/pms/role`
  - `GET /api/v1/pms/role/:id`
  - `PUT /api/v1/pms/role/:id`
  - `DELETE /api/v1/pms/role/:id`
- root 授权：
  - `GET /api/v1/pms/root/uids`
  - `POST /api/v1/pms/root/grant`
- 实例角色授权：
  - `GET /api/v1/pms/instance/:iid/role/grant`
  - `PUT /api/v1/pms/instance/:iid/role/grant`
- 权限公共信息：
  - `GET /api/v1/pms/commonInfo`

### v2 首期缺口

如果仅复用现有接口，v2 前端可以先落地，但为了支持“用户主线”页面，缺少面向用户视角的聚合查询能力。

建议首期补一个或两个 v2 聚合接口，而不是直接把前端完全建立在多接口拼装上。

建议新增：

- `GET /api/v2/base/permission/users/:uid/grants`
  返回某个用户的授权总览，按实例、角色、domain 聚合
- `PATCH /api/v2/base/permission/users/:uid/grants`
  以用户为主线增删改授权关系

可选新增：

- `GET /api/v2/base/permission/instances/:iid/grants`
  返回某实例下的角色与用户授权关系
- `GET /api/v2/base/permission/root-users`
- `PUT /api/v2/base/permission/root-users`

## 前端实施结构

建议在 `ui-v2/src/domains/settings` 下继续扩展，或拆出独立 `permission` domain。

推荐采用独立 domain：

- `ui-v2/src/domains/permission/api/permission.ts`
- `ui-v2/src/domains/permission/pages/PermissionUsersPage.tsx`
- `ui-v2/src/domains/permission/pages/PermissionRolesPage.tsx`
- `ui-v2/src/domains/permission/pages/PermissionResourcesPage.tsx`
- `ui-v2/src/domains/permission/pages/PermissionRootPage.tsx`
- `ui-v2/src/domains/permission/components/*`

路由建议：

- `/v2/permission/users`
- `/v2/permission/roles`
- `/v2/permission/resources`
- `/v2/permission/root`

导航建议：

- 在 `AppShell` 中新增“权限中心”
- 进入后展示二级导航或 tab

## 分阶段实施计划

### Phase 1：基础能力与骨架

- 新增 v2 权限中心导航与路由
- 落地“用户与授权”页面骨架
- 接入现有 v2 用户管理接口
- 接入现有 v1 角色、root、实例授权接口
- 补齐必要的类型定义与 API 封装

验收标准：

- 能在 v2 查看用户列表
- 能创建、编辑、删除、重置密码
- 能看到角色列表与 root 列表基础数据

### Phase 2：用户主线授权闭环

- 实现用户详情与授权面板
- 支持查看某用户当前授权
- 支持为用户新增、编辑、删除授权
- 如需要，补充用户视角聚合接口

验收标准：

- 在 v2 可完成“给某用户授予某实例某角色”的完整闭环

### Phase 3：角色模板与资源范围

- 实现角色模板管理页
- 实现资源范围页
- 支持按实例排查当前授权关系

验收标准：

- 角色与资源视图都能完成日常维护

### Phase 4：Root 管理

- 实现 root 管理页
- 增加高风险提示和二次确认
- 明确交互限制，避免误操作

验收标准：

- root 用户可在 v2 中查看、授予、撤销

## 风险与应对

### 风险 1：v1 接口语义偏资源主线

影响：

- 不利于直接支持用户主线交互

应对：

- 首期允许前端聚合
- 第二步再补用户主线聚合接口

### 风险 2：root 与普通权限混淆

影响：

- 高风险误操作

应对：

- Root 管理单独页面
- 明确视觉隔离、说明文案、二次确认

### 风险 3：页面范围较大

影响：

- 一次性实现容易失控

应对：

- 分阶段落地
- 优先完成用户主线闭环

## 验收标准

最终完成后，v2 应满足：

- 能在 v2 管理用户
- 能在 v2 管理角色
- 能在 v2 绑定实例、角色与用户
- 能在 v2 管理 root 用户授权
- 常见授权流程可在“用户与授权”中闭环完成
- 资源视角仍能查看和排查授权关系

## 推荐实施顺序

推荐按以下顺序执行：

1. 权限中心路由与导航骨架
2. 用户管理迁入 v2
3. 用户主线授权闭环
4. 角色模板页
5. 资源范围页
6. Root 管理页

## 结论

本次采用“用户主线型权限中心”作为 v2 权限管理方案。它比 v1 更符合日常授权动作，同时保留角色模板、资源视角和 root 独立管理，能够在不推翻现有权限模型的前提下完成更合理的 v2 实施。
